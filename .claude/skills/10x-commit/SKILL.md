# /10x-commit — Commit & Push with Ticket Reference

Stage changes, commit with a ticket/issue reference and a short description, then push. Auto-detects ticket numbers from the conversation context. If the conversation spans a single ticket, uses it automatically. If zero or multiple tickets are found, asks the user to specify. Creates a new branch from `main` (or a user-specified base branch) named `<ticket>-<short-slug>` if one doesn't already exist.

## When to use

After implementing a change or fix — when the work is done and you want to land it on a branch with a properly referenced commit.

## Initial Response

When invoked:

1. If `[file paths to stage]` arguments were provided, use them. Otherwise default to staging all tracked, modified files (`git add -u`) plus new untracked files in the working tree.
2. Proceed to Step 1.

## Workflow

### Step 1 — Detect ticket reference

Scan the **current conversation context** for ticket/issue identifiers:

| System | Pattern | Example |
|---|---|---|
| GitHub issue | `#<number>` | `#1`, `#42` |
| GitHub issue URL | `github.com/<owner>/<repo>/issues/<N>` | `#1` |
| Linear | `<TEAM>-<number>` | `TEN-14`, `ENG-3` |
| Jira | `<PROJECT>-<number>` | `ABC-123`, `PROJ-4567` |
| Roadmap ID | `F-\d{2}`, `S-\d{2}` | `F-01`, `S-02` |
| Change ID | kebab-case folder under `context/changes/` | `data-schema` |

**Rules:**

- **Exactly one ticket found** → use it automatically. Print: `Detected ticket: <ticket>` and proceed to Step 2.
- **Zero tickets found** → ask via `AskUserQuestion`:

  ```
  question: "No ticket reference found in the conversation. Which ticket does this commit belong to?"
  header: "Ticket"
  options:
    - label: "Enter ticket number"
      description: "I'll type it in (e.g. #1, TEN-14, ABC-123)."
  ```

  On "Enter ticket number": accept free-text input, validate it looks like a ticket reference, proceed to Step 2.

- **Multiple tickets found** → ask via `AskUserQuestion`:

  ```
  question: "Multiple ticket references found in the conversation. Which one does this commit belong to?"
  header: "Ticket"
  options:
    - label: "<ticket-A>"
      description: "<where it appeared in conversation>"
    - label: "<ticket-B>"
      description: "<where it appeared in conversation>"
    ...
    - label: "None of these — I'll specify"
      description: "Enter a different ticket reference."
  ```

### Step 2 — Collect commit description

Ask for a short description:

```
question: "What short description for the commit message?"
header: "Description"
options:
  - label: "<auto-generated from context> (Recommended)"
    description: "Derived from the phase name, change-id, or task description found in conversation."
  - label: "I'll write my own"
    description: "Free-text short description."
```

If the user picks "I'll write my own", accept free-text. The description should be ≤ 72 characters, imperative mood (e.g. "add drift persistence layer", "fix overstuffing calc").

### Step 3 — Branch management

1. **Check current branch:**

   ```bash
   git branch --show-current
   ```

2. **Propose branch name:** `<ticket>-<short-slug>` where `<short-slug>` is 2-4 kebab-case words from the description.

   Example: `#1-data-schema-crud`, `TEN-14-review-session`, `F-01-trip-attraction-entities`

3. **Check if branch already exists:**

   ```bash
   git branch --list "<proposed-branch>"
   git branch --list -r "origin/<proposed-branch>"
   ```

   - **Branch exists and we're on it** → skip branch creation, proceed to Step 4.
   - **Branch exists but we're NOT on it** → ask via `AskUserQuestion`:
     ```
     question: "Branch <proposed-branch> already exists. Switch to it?"
     header: "Branch"
     options:
       - label: "Switch to existing branch (Recommended)"
         description: "Checkout <proposed-branch> and commit there."
       - label: "Stay on current branch"
         description: "Commit on <current-branch> instead."
       - label: "New branch name"
         description: "I'll specify a different branch name."
     ```
   - **Branch does NOT exist** → create it:

     ```bash
     git checkout -b "<proposed-branch>" <base-branch>
     ```

     Where `<base-branch>` defaults to `main`. If the user passed a different base (e.g. `/10x-commit @feature-branch`), use that instead.

     Ask once via `AskUserQuestion` if the base should be something other than `main`:
     ```
     question: "Create branch <proposed-branch> from main?"
     header: "Base branch"
     options:
       - label: "Yes — branch from main (Recommended)"
         description: "Standard flow. New branch off main."
       - label: "Branch from something else"
         description: "I'll specify the base branch."
     ```

### Step 4 — Stage files

- If file paths were provided as arguments, stage exactly those: `git add <file1> <file2> ...`
- Otherwise, stage all changes: `git add -A`

Print the list of staged files so the user can verify:

```bash
git diff --cached --name-status
```

Ask to confirm:

```
question: "Stage these files?"
header: "Stage"
options:
  - label: "Yes — commit these files (Recommended)"
    description: "Proceed with the listed files."
  - label: "Let me narrow it down"
    description: "I'll specify which files to include/exclude."
  - label: "Abort"
    description: "Don't commit anything."
```

### Step 5 — Commit

Build the commit message:

```
<type>(<scope>): <ticket> <short-description>

Refs: <ticket-reference>
```

Where:
- `<type>` is `feat` / `fix` / `chore` / `refactor` — inferred from the description
- `<scope>` is the change-id or module name
- `<ticket>` is the ticket reference from Step 1

Example: `feat(data-schema): #1 add drift persistence layer`

Present the message and ask for approval:

```
question: "Approve commit message?"
header: "Commit msg"
options:
  - label: "Approve as proposed (Recommended)"
    description: "Use the message as drafted."
  - label: "Edit message"
    description: "I'll modify the subject or body."
  - label: "Abort"
    description: "Don't commit."
```

Execute:

```bash
git commit -m "$(cat <<'EOF'
<type>(<scope>): <ticket> <short-description>

Refs: <ticket-reference>
EOF
)"
```

Never pass `--no-verify` or `--amend` unless the user explicitly requests it.

### Step 6 — Push

```bash
git push -u origin <branch-name>
```

If the remote branch already exists (not the first push), use `git push` without `-u`.

Print a success summary:

```
═══════════════════════════════════════════════════════════
  COMMITTED & PUSHED
═══════════════════════════════════════════════════════════

  Branch:    <branch-name>
  Ticket:    <ticket>
  Commit:    <short-sha> — <subject-line>
  Remote:    origin/<branch-name>
═══════════════════════════════════════════════════════════
```

## Guardrails

1. **Never commit without a ticket reference.** If Step 1 can't resolve a ticket, ask — don't guess.
2. **Never commit secrets.** Before staging, scan the diff for patterns like `-----BEGIN`, `api_key`, `token`, `password`, `secret`. If found, abort and warn the user.
3. **Never amend pushed commits.** If `--amend` is requested, check if the commit was already pushed (`git branch -r --contains HEAD`). Warn and refuse if so.
4. **Branch names are kebab-case.** `<ticket>-<short-slug>` — no spaces, no underscores, no special chars beyond hyphens.
5. **Push is always explicit.** Never push without the user approving the commit message (Step 5) — that's their last gate.
